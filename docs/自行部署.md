# 自行部署联机服务器

[返回项目首页](../README.md) · [游戏玩法](游戏玩法.md)

本项目是一个 Node.js 服务：同一个进程提供游戏网页、账号接口和 `/ws` WebSocket 联机入口。账号、会话、历史战绩和军衔结算保存在 SQLite；在线名单、房间和未结束的比赛保存在进程内存。以下步骤适用于单台 Linux 服务器。

## 部署前准备

- Linux `x86_64` 或 `aarch64`，以及项目完整文件；安装依赖时需要能访问 npm。安装脚本在缺少 Node.js 24+ 时还需要能下载 Node.js 发布包。
- 一个供玩家访问的域名和 HTTPS 反向代理。邮箱密码、验证码及登录 Cookie 应通过 HTTPS 传输；只在本机调试时使用 `http://localhost:8787`。
- 一个已开通 SMTP 发信权限的邮箱，取得服务器地址、端口、登录账号和授权码。注册及找回密码必须能发信。
- 服务器上的项目目录需要有持久存储空间和写权限；不要把 SQLite 数据库放在每次发布都会被清空的临时目录。

不需要另装 Redis、MySQL 或独立静态网页服务。当前实现只支持一个游戏服务实例维护全部房间；多进程或多机负载均衡不能直接共享房间状态。

## 安装和首次启动

把项目放到目标目录后，进入**项目根目录**执行：

```bash
./deploy/install.sh
```

脚本优先使用系统中已有的 Node.js 24+；否则下载适合本机架构的 Node.js 24 包，校验 SHA-256，并安装在项目的 `.runtime/node`，不会覆盖系统 Node.js。旧版 glibc 的 x86_64 Linux 可能使用社区维护的兼容构建。然后脚本在 `server/` 下执行 `npm ci --omit=dev`，并在首次安装时从示例生成 `deploy/config.env`。`config.env` 已存在时不会覆盖它。

**先编辑配置，再启动服务**：

```bash
chmod 600 deploy/config.env
./deploy/start.sh
./deploy/status.sh
curl http://127.0.0.1:8787/health
```

默认监听 `0.0.0.0:8787`。`start.sh` 在后台运行，记录进程 ID 至 `.runtime/server.pid`，日志写入 `.runtime/server.log`；`status.sh` 会检查进程和健康接口。端口修改后，将健康检查命令中的 `8787` 同步改掉。若保持默认监听地址，可用 `http://服务器地址:8787/transport-ship-mp.html` 检查直连；设为 `HOST=127.0.0.1` 后只能在服务器本机直连，应使用下文的 HTTPS 域名访问。

### 配置邮箱注册、找回密码与好友邀请

在 `deploy/config.env` 中填写自己的发信账号信息。以下值**只是格式示例**：

```bash
PORT="8787"
HOST="127.0.0.1"
PUBLIC_ORIGIN="https://game.example.com"
SMTP_HOST="smtp.example.com"
SMTP_PORT="465"
SMTP_USER="sender@example.com"
SMTP_PASS="你的 SMTP 授权码"
SMTP_FROM="sender@example.com"
RANK_XP_ENABLED="1"
```

`SMTP_PORT=465` 使用 SSL；`587` 使用 STARTTLS。`SMTP_PASS` 通常是邮箱服务商给的 SMTP 授权码，具体服务器、端口、授权方式以邮箱服务商说明为准。`config.env` 是 Shell 配置文件，包含凭据，请限制文件权限，不要提交到 Git 或贴到公开日志。修改配置后执行 `./deploy/stop.sh` 和 `./deploy/start.sh`。

| 变量 | 默认值 | 用途 |
|---|---|---|
| `PORT` | `8787` | Node.js 监听端口 |
| `HOST` | `0.0.0.0` | 监听地址；同机反向代理时建议 `127.0.0.1` |
| `PUBLIC_ORIGIN` | 空 | 浏览器对外访问的准确来源地址，例如 `https://game.example.com`，不要带路径或末尾 `/` |
| `SMTP_HOST`、`SMTP_PORT` | 空、`465` | SMTP 服务器与端口 |
| `SMTP_USER`、`SMTP_PASS`、`SMTP_FROM` | 空 | SMTP 登录名、授权码、发件地址 |
| `AUTH_DB_PATH` | `.runtime/accounts.sqlite` | 可选数据库文件路径；自定义时建议使用绝对路径 |
| `RANK_XP_ENABLED` | `1` | `1` 发放合格比赛的军衔经验；`0` 暂停之后新开始比赛的经验发放 |

未配置 SMTP 时，已有账号仍可用密码登录，但新用户无法收取注册验证码，也无法通过邮件找回密码。注册验证码 10 分钟有效，重发至少间隔 60 秒。登录会话保留 30 天；重置密码后旧会话会失效。

离线好友邀请共用上述 SMTP 配置。公网访问要求 `PUBLIC_ORIGIN` 为实际 HTTPS 域名；从本机 `localhost`、`127.0.0.1` 或 `[::1]` 访问时可留空，服务端会用当前本机访问地址生成链接。邮件链接 30 分钟内可用一次；点击后自动登录受邀账号。有房间时尝试入房，房间已失效时返回房间列表。更新服务端代码后需要重启 Node.js 进程；重启会清空内存中的房间，已发的房间邀请链接因此会回退到房间列表。

### 用 HTTPS 对外提供服务

推荐让反向代理占用公网 80/443，让游戏进程只监听本机 `127.0.0.1:8787`。域名解析到服务器后，以 Caddy 为例：

```caddyfile
game.example.com {
    reverse_proxy 127.0.0.1:8787
}
```

将 `PUBLIC_ORIGIN` 设为玩家实际打开的地址 `https://game.example.com`。反向代理需要把网页、`/api/` 和 `/ws` 都转发到同一个 Node.js 进程，并支持 WebSocket 升级；上述 Caddy 配置会转发全部路径。玩家访问 `https://game.example.com/transport-ship-mp.html`，浏览器会使用同源的 `wss://game.example.com/ws`。云防火墙放行 80/443；若 Node.js 只绑定本机，无需对公网放行 8787。

访问 `http://服务器地址/` 时若出现另一个站点或 404，通常是 80 端口正由其他服务处理，而游戏运行在 8787。检查反向代理站点配置和域名指向，不要仅凭 `/health` 在本机可用就认为公网入口已经接通。

## 日常管理、更新与备份

### 从本地一条命令部署到现有服务器

在本项目本地根目录执行：

```bash
./deploy/remote.sh
```

首次使用先在本机创建 `deploy/remote.local.sh`，填写自己的服务器信息：

```bash
DEPLOY_TARGET="user@game.example.com"
DEPLOY_PATH="/srv/transport-ship"
```

该文件已加入 `.gitignore`，部署时也不会上传。可用同名环境变量临时覆盖配置。本机需安装 `ssh` 和 `rsync`，并能 SSH 登录远端；推荐配置 SSH 密钥，否则运行时会交互输入几次 SSH 密码。脚本不保存密码。

它会上传当前工作目录到远端临时目录，校验游戏构建产物和服务端语法，停服后备份完整项目（不含可重新安装的 `node_modules`），覆盖代码，执行安装脚本并启动服务，最后检查健康接口、联机页面和游戏脚本。`deploy/config.env`、`.runtime/` 不会从本地上传，线上账号数据库和邮件配置会保留。失败时脚本尝试从刚生成的备份恢复旧版本并重新启动；发布成功后，部署目录同级的 `<目录名>-backups/` 只保留刚生成的一份升级前备份。服务重启会让在线玩家断线，因此建议在房间空闲时执行。首次部署仍按上文手动完成邮箱配置。

部署后用自己的服务器地址或已配置的 HTTPS 域名打开 `/transport-ship-mp.html`。若服务器修改了 `PORT`，脚本会读取远程配置进行健康检查。自定义 `AUTH_DB_PATH` 指向项目目录外时，该外部数据库不在项目备份中，需要单独备份。

### 服务器本机管理

在项目根目录执行：

```bash
./deploy/status.sh
tail -f .runtime/server.log
./deploy/stop.sh
./deploy/start.sh
```

这些脚本通过 PID 文件识别本项目进程，`stop.sh` 只停止由该脚本启动且仍属于本项目的服务。它们**不提供开机自启或进程崩溃自动拉起**；有此需求可单独配置 systemd 等服务管理器，但不要同时用两套方式占用同一端口。

更新代码时，先停止服务，保留 `deploy/config.env` 和 `.runtime/accounts.sqlite`，更新项目文件，再运行安装与启动脚本：

```bash
./deploy/stop.sh
./deploy/install.sh
./deploy/start.sh
./deploy/status.sh
```

如果是把新版文件复制到一个新目录，先把旧目录的 `deploy/config.env` 和数据库复制到新目录对应位置，再启动新版本。**不要用会删除目标目录独有文件的同步选项清空 `.runtime/`**。升级前建议备份配置和数据库。

最简单可靠的数据库备份方式是先 `./deploy/stop.sh`，复制 `.runtime/accounts.sqlite`，再启动服务。运行中备份时需要正确处理 SQLite WAL 模式产生的 `accounts.sqlite-wal` 等伴随文件，不能只复制主数据库文件。数据库保存账号、会话、历史榜战绩及已完成的军衔结算；`.runtime/server.log` 用于排障，`.runtime/node` 可由安装脚本重新获取。备份文件同样包含敏感账号数据，应限制访问权限。

重启会清空在线列表、房间和正在进行的比赛，玩家要重新入房。未正常结束的比赛不补发经验；已持久化结束但尚未完成的结算会在服务启动时重试。

## 排障顺序

1. **页面打不开**：先运行 `./deploy/status.sh` 和 `curl http://127.0.0.1:8787/health`；再看 `.runtime/server.log`、监听端口、反向代理、DNS 与防火墙。若端口不是 8787，改用配置中的 `PORT`。
2. **页面可打开但联机失败**：确认浏览器和 WebSocket 使用同一 HTTPS 域名，反向代理转发了 `/ws`，并核对 `PUBLIC_ORIGIN` 是否与浏览器地址完全一致。检查浏览器开发者工具中的 WebSocket 请求及服务器日志。
3. **注册或找回密码无法收信**：核对 SMTP 地址、端口、发信授权码、发件地址和服务器到邮件服务商的网络；查看日志中的发信错误。不要把授权码直接发给玩家排查。
4. **登录后房间/排行榜数据为空**：确认正在访问同一台服务实例、数据库文件没有在更新时被替换；实时房间在重启后清空属于当前架构的正常行为。
5. **启动时报端口被占用**：检查是否已有本项目进程或其他服务占用 `PORT`，避免同时运行 `npm start`、本机启动器和 `deploy/start.sh`。

## 本机与 Windows 补充

macOS 可双击根目录的 `启动联机.command`；它会读取现有的 `deploy/config.env`。Windows 可双击 `start-windows.bat`；该批处理使用当前环境变量，不读取 `config.env`。在 Windows 上首次注册前，先在同一终端设置 SMTP 环境变量，再运行批处理或进入 `server/` 执行 `npm ci`、`npm start`。两种启动器都是前台运行，关闭窗口就会停止服务。正式长期对外服务建议使用上面的 Linux 部署方式。
