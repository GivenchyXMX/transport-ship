# 好友、玩家目录与邀请系统设计

状态：已按本文实现第一版。本文基于当前单进程 Node.js + WebSocket + SQLite 架构；房间和进行中的比赛仍保存在进程内存中。

## 1. 目标与界面

联机页面右侧改为两个页签：**好友**、**所有玩家**。好友页默认按状态、昵称排序，并显示收到的好友申请数量；所有玩家页提供昵称搜索和分页，列出所有已注册账号（不显示本人）。两页中的玩家行统一显示昵称及其后面的邮箱、状态圆点、状态文字和“最近上线”时间。登录凭据和 IP 地址不出现在玩家目录或 WebSocket 消息中。

| 状态 | 圆点 | 判定 | 行内文字 |
|---|---|---|---|
| 在线 | 绿 | 账号有有效 WebSocket 连接，且不在房间 | 在线 |
| 在房间 | 黄 | 账号在房间等待、准备，或在进行中的房间里等待选择阵营/加入战斗 | 在房间；可附房间名 |
| 战斗中 | 红 | 房间正在对战，且该玩家已进入战斗（`pendingBattle === false`） | 战斗中 |
| 离线 | 灰 | 没有有效 WebSocket 连接 | 离线 |

“最近上线”统一指该账号最近一次成功建立联机 WebSocket 连接的时间 `last_online_at`；从未连接过显示“从未上线”。离线玩家额外显示 `last_seen_at`（最后一次确认在线的时间），避免把“最近上线”误读为下线时间。界面用北京时间展示，悬停或展开时给出完整时间。HTTP 登录成功但 WebSocket 尚未连上时仍为离线。网络断开并重连后，按新连接状态重新计算。

好友行提供“邀请”“删除好友”；所有玩家和房间内的玩家行提供“加好友”。已是好友、已发出申请、待我处理的申请分别显示明确状态，避免重复发送。窄屏时右侧面板折叠成可展开页签，不遮住房间操作。

## 2. 好友申请与删除

1. 登录用户可从房间名单或“所有玩家”选择其他注册账号，点击“加好友”。请求只包含目标账号 ID；发送者由当前登录会话确定。不能给自己发送，也不能对已有好友重复发送。
2. 申请写入 SQLite。目标在线时实时收到申请提示；离线时下次打开联机页面能在“收到的申请”中看到。首版不为好友申请发邮件。
3. 收件人可“接受”或“拒绝”。接受时在同一事务内把申请置为已接受并创建一条双向好友关系；拒绝只更新申请状态。双方在线时立即刷新好友列表。反向申请已经存在时，提示用户处理收到的申请，不自动接受。
4. 任一方可删除好友；服务端删除这一条双向关系，并通知双方刷新列表。删除后允许重新申请，未过期的离线邀请链接同时失效。

服务端限制待处理申请数量和发送频率，并对同一目标设置冷却时间；具体上限作为常量集中配置。界面展示服务端返回的冷却或失败原因，不把昵称当作唯一标识。

## 3. 房间邀请与离线邮件

### 在线玩家

保留现有 30 秒房间邀请的“接受 / 拒绝”弹窗。发起者在房间内时，可以从好友页、所有玩家页或当前在线名单邀请**任何在线且空闲的注册玩家**，好友和陌生玩家均可。后端使用稳定的 `accountId` 定位目标连接，仍检查房间空位、剩余比赛时间、踢出名单和目标是否已经入房。接受后沿用现有 `join` 规则；进行中的比赛先进入房间选队页，再由玩家点击“加入战斗”。

在线目标已在其他房间或战斗中时不提供直接房间邀请，显示其状态；房间内玩家仍可收到好友申请。没有房间时不提供房间邀请。

### 离线好友

- 发起者**在房间内**：好友行提供“一键邀请入房”。服务端向离线好友的注册邮箱发送邮件，邮件说明邀请人、房间名、有效期和一个“进入房间”链接。
- 发起者**不在房间内**：好友行提供“邀请上线”。邮件链接登录后进入联机大厅的房间列表。
- 离线陌生玩家可收到好友申请，但不能发送免登录邮件邀请；这防止“所有玩家”目录被用来批量给陌生邮箱发信。
- 邮件发送失败时明确告知发起者，不显示“已邀请”。同一发起者与目标之间设置冷却时间，并限制每账号每日发送量及目标每日收件量。

邮件链接中的随机令牌仅供目标账号使用，30 分钟有效、只能兑换一次。邮件不会包含密码或常规登录会话。房间邀请记录同时保存房间 ID 和随机的**房间实例 ID**；当前房间 ID 可能在服务重启后复用，实例 ID 可防止旧邮件误入新房间。

### 点击邮件链接

1. 链接打开同源的轻量 `/invite.html#token=...`。令牌放在 URL fragment，页面立即从地址栏移除 fragment，再通过同源 `POST /api/social/invitations/redeem` 兑换；该页面不加载第三方脚本或图片，并设置 `Referrer-Policy: no-referrer`、`Cache-Control: no-store`。
2. 服务端在事务中验证令牌哈希、目标账号、有效期、未使用状态和好友关系，然后原子地标记已使用，并为目标账号创建现有格式的 HttpOnly 标签页会话 Cookie。新页面沿用 `X-Ship-Tab` / `ship_session_<tabId>` 机制。若浏览器当前标签已登录其他账号，先显示将切换到受邀账号的确认页，避免静默替换身份。
3. 兑换成功后，同一标签页跳转游戏页面。临时入房意图只放在该标签页的 `sessionStorage`，包含房间 ID 与实例 ID，不再携带登录令牌。联机 WebSocket 建立后自动尝试加入该房间；后端再次验证实例 ID 并沿用普通入房条件。
4. 若房间已删除、实例不匹配、已满、受邀者被踢出，或比赛即将结束，则进入**联机大厅的房间列表**并显示具体原因。发起者不在房间时的“邀请上线”也直接进入房间列表。进行中的房间可加入时，先进入选阵营页，不自动参战。
5. 令牌过期、已用或无效时不自动登录；显示可理解的提示和正常登录入口。浏览器或邮件客户端的链接预览只会 GET 页面，不会消耗令牌。用户打开同一链接两次时，第二次按失效链接处理；已建立的正常登录会话不被清除。

公网邮件链接需要准确的 HTTPS `PUBLIC_ORIGIN`。本机回环地址访问时可留空 `PUBLIC_ORIGIN`，服务端只接受实际来自回环地址且 `Host` 是 `localhost`、`127.0.0.1` 或 `[::1]` 的请求，用该本机地址生成链接。未配置 SMTP，或公网访问未配置外部地址时禁用离线邮件邀请并展示配置原因；不能从任意请求的 `Host` 头拼接登录链接。

## 4. 数据与状态来源

新增表（字段名为设计建议）：

| 表 / 字段 | 内容与约束 |
|---|---|
| `accounts.last_online_at` | 最近一次联机 WebSocket 建立时间，可为空；注册时不算上线 |
| `accounts.last_seen_at` | 最后一次确认在线时间；连接期间限频更新，正常断线时更新，异常退出时保留最近心跳时间 |
| `friend_requests` | `id`、`sender_id`、`recipient_id`、`status`（pending/accepted/declined）、`created_at`、`decided_at`；同一对账号最多一条待处理申请 |
| `friendships` | `account_low`、`account_high`、`created_at`；账号 ID 按固定顺序存储，复合主键保证双向关系不重复 |
| `offline_invitations` | `id`、`token_hash`、`sender_id`、`target_id`、`kind`（room/online）、`room_id`、`room_instance_id`、`created_at`、`expires_at`、`consumed_at`、`delivery_status` |

在线状态仅由进程内已认证 WebSocket 连接和房间状态计算，不把“在线/战斗中”写成持久字段。连接、断线、入房、离房、开战、赛后回房、待加入玩家正式入战时都要推送状态变化。当前一个账号只保留一个联机连接；若未来允许多连接，只有最后一条连接断开才可标记离线。

列表读取与 WebSocket 更新可能交错：每次状态快照带服务器时间或递增版本；重连后重新拉取好友、申请和当前玩家目录页，避免漏事件。好友关系、申请和最近上线时间在服务重启后保留；所有房间在重启后消失，邮件入房链接因此按“房间不存在”回退。

## 5. 接口与消息建议

目录、好友及发送邀请的接口均需现有登录 Cookie、`X-Ship-Tab`，并执行同源检查。邮件令牌兑换接口是例外：允许未登录用户调用，但必须校验一次性令牌、`X-Ship-Tab` 和同源请求，再建立受邀账号会话。登录后的目录和房间响应包含界面展示所需的 `accountId`、昵称、邮箱、状态、时间、好友关系和可操作性。

| 接口或消息 | 用途 |
|---|---|
| `GET /api/social/players?q=&cursor=&limit=` | 所有注册玩家的搜索与分页；默认不返回本人，限制最大 `limit` |
| `GET /api/social/friends` | 好友列表及当前状态 |
| `GET /api/social/requests` | 收到与发出的待处理申请 |
| `POST /api/social/requests` | 按 `targetAccountId` 发送好友申请 |
| `POST /api/social/requests/:id/respond` | 仅收件人接受或拒绝 |
| `DELETE /api/social/friends/:accountId` | 删除双向好友关系 |
| `POST /api/social/invitations` | 服务端根据发起者是否在房间、目标是否在线决定实时房间邀请或离线邮件邀请 |
| `POST /api/social/invitations/redeem` | 兑换邮件中的一次性令牌并建立目标账号会话 |
| `social_presence`、`social_request`、`social_friend` | WebSocket 推送在线状态、申请和好友关系变更；连接恢复后仍以 HTTP 快照校准 |

房间快照和玩家目录需提供稳定 `accountId`，现有 `netId` 继续用于实时战斗与旧邀请兼容。邀请的发送者、目标、房间和可加入性由服务端依据会话与当前状态确定，不信任客户端提供的状态、邮箱或房间名。网页只在右侧面板显示当前目录页，服务端对好友和正在查看的账号推送状态，避免每次状态变化向所有在线用户发送完整账号目录。

## 6. 实施顺序与验收

1. 增加 SQLite 迁移、好友数据访问层及最近上线时间记录；旧账号的时间允许为空。
2. 增加玩家目录、好友申请与删除接口，以及 WebSocket 状态更新；先完成右侧好友/所有玩家面板和房间名单“加好友”。
3. 将在线房间邀请改为稳定账号 ID 定位，保留现有接受/拒绝与全部房间校验。
4. 增加离线邮件邀请、一次性令牌兑换页面与自动入房意图；最后接通失效房间回退和发送限流。

验收场景：四种颜色随连接与房间/战斗状态切换；从房间和玩家目录发申请、接受、拒绝、删除后双方列表一致；在线好友和陌生玩家均可收到房间邀请；离线好友在有房和无房两种情况下收到对应邮件；有效链接自动登录并入房或进入房间列表；房间删除、服务重启、房满、踢出、链接过期/复用、错误账号登录与邮件发送失败都有明确结果，且不能绕过原有入房限制。
