# 多地图扩展与功能拆分技术方案

> 状态：阶段 1–3 的架构拆分已实现，待使用者按[黑盒测试清单](架构拆分黑盒测试清单.md)完成功能验收。现有脚本仍是按确定顺序拼接的过渡结构，原压缩代码尚未整体改写为独立 ES 模块。当前房间已提供选图入口及 ID/版本协议，但可选目录只有运输船；第二张地图和实际切图加载留待后续。

## 1. 目标与范围

- 将游戏运行、地图、武器、角色与 bot、界面、联机适配拆成边界清晰的模块，保留现有 `/transport-ship-mp.html` 入口。
- 地图由房间选定；同一房间在一局比赛中使用同一个不可变的地图 ID 和版本。大厅、等待页、开局和中途加入都展示或传递该地图。
- 客户端渲染、移动碰撞、雷达、bot 寻路，以及服务端移动校验、弹道遮挡和出生点验证使用一致的地图数据约定。
- 第一阶段只支持现有团队竞技规则。爆破等新模式另建规则模块，不能仅通过换地图实现。
- 不在拆分阶段重写射击手感、网络权威模型或账号、军衔和战绩规则。
- 架构阶段不增加创建房间的入口或参数，也不新增房间。验证联机功能时使用现有房间流程；如果暂时不运行双人联机，可先完成静态检查和单机冒烟，双人回归仍是最终验收门槛。

## 2. 改造前基线与主要耦合

| 功能 | 当前代码 | 扩图时的问题 |
| --- | --- | --- |
| Three.js、材质生成、地图几何、物理、导航、bot、武器、HUD、游戏主循环 | `transport-ship-mp.html` 内嵌脚本，包含压缩后的第三方库和游戏代码 | 地图与玩法混在单个大文件中，难以独立开发和审查 |
| 运输船场景 | 内嵌 `Rf(...)` 生成贴图、`If(...)` 构造场景及客户端碰撞体 | `If(...)` 同时返回出生点、灯光等信息；场景切换不是独立接口 |
| 客户端移动与 AI | 内嵌 `gr` 碰撞世界、`Ql` 网格寻路、`Fa` bot；初始化直接构建运输船 | 寻路边界、bot 目标点、雷达范围都写死了运输船坐标 |
| 联机适配 | `web/mp.js` 通过 `window.__game` 和覆盖游戏方法接入 | 原版开局先生成 bot 再替换为远端角色，加载新地图时生命周期不清晰 |
| 房间与 UI | `web/room.js`、`web/ui.js` | 房间创建消息不带地图；等待页海报和名称固定为运输船 |
| 服务端房间与裁决 | `server/server.js`、`server/combat.js` | 房间 `map` 固定为 `transport-ship`；服务端碰撞体、出生点是客户端数据的手写副本；位置边界写死 |
| 静态资源 | `web/assets/maps/`，`server/server.js` 的 `PUBLIC_FILES` | 地图海报、脚本等新增文件需要同步发布；应检查路径与实际文件一致 |

现有联机权威边界保持不变：客户端预测并上报位置，服务端校验速度、穿越和真人伤害；bot 仍由房主客户端模拟。多地图改造必须让服务端按**房间地图**选择碰撞数据，不能继续使用单例 `combat.WALLS`、`combat.SPAWNS` 或固定的运输船边界。

## 3. 建议的模块边界

以下是后续可演进的**目标目录示意**。当前阶段已先按职责拆成 `.part.js` 文件，由 `scripts/build-game.cjs` 拼接为现有页面加载的 `web/game.js`，仍共享原 IIFE 闭包；实际目录见 README。

```text
src/client/
  main.js                 页面启动、依赖组装和地图加载
  core/game.js            对局生命周期、主循环和通用状态
  core/renderer.js        Three.js 场景、相机、画质和环境
  core/world.js           客户端碰撞与移动
  actors/player.js        本地玩家
  actors/bot.js           bot 行为；目标点从地图配置读取
  actors/remote.js        远端角色与状态插值
  combat/weapons.js       武器表现和客户端射击反馈
  navigation/grid.js      根据地图范围和碰撞体建网格
  ui/game-hud.js          HUD、计分板、雷达画布
  multiplayer/adapter.js  对接 web/net.js、web/room.js 的游戏事件
  maps/registry.js        地图 ID 到地图包的注册和按需加载
  maps/transport-ship/scene.js      运输船几何、材质和环境特效
  maps/transport-ship/bot.js        运输船特定路线、守点
shared/maps/transport-ship.json      客户端与服务端共用的地图规则数据
server/maps.js             加载并校验地图规则数据
server/combat.js           通用命中计算，接收地图碰撞体参数
server/server.js           房间与 WebSocket 编排，按 room.map 取地图
web/assets/maps/transport-ship/     海报及未来外部贴图或模型
```

`shared/maps/*.json` 应只放可序列化、两端必须一致的规则数据；Three.js 材质、复杂网格和视觉特效留在 `scene.js`。服务端不加载渲染代码。武器数值目前同时出现在客户端内嵌代码与 `server/combat.js`，可在地图迁移稳定后另行统一，避免一个改造同时影响地图和伤害平衡。

## 4. 地图接口与数据契约

每张地图导出稳定的 `id`、`version`，并实现客户端场景加载与释放。建议接口形状如下，字段名在实施时可微调，但语义要固定：

```js
// 客户端地图包
export const manifest = { id: 'transport-ship', version: 1, mode: 'team-deathmatch' };
export async function loadMap({ scene, quality, rules }) {
  // 创建网格、材质、灯光和特效；从 rules 创建客户端碰撞世界
  return { world, spawns: rules.spawns, update: (dt) => {}, dispose: () => {} };
}
```

```json
{
  "id": "transport-ship",
  "version": 1,
  "mode": "team-deathmatch",
  "displayName": "运输船",
  "poster": "/web/assets/maps/transport-ship/poster.png",
  "bounds": { "minX": -36.5, "maxX": 36.5, "minY": -0.5, "maxY": 8, "minZ": -12.4, "maxZ": 12.4 },
  "nav": { "minX": -36.2, "maxX": 36.2, "minZ": -12.1, "maxZ": 12.1, "cell": 0.5, "radius": 0.42 },
  "radar": { "minX": -37, "maxX": 37, "minZ": -13, "maxZ": 13 },
  "spawns": { "BL": [], "GR": [] },
  "colliders": []
}
```

上例是**结构示意**，空数组不能作为可运行地图。迁移运输船时，应从现有 `If(...)`、`server/combat.js` 逐项提取真实出生点和碰撞体，并检查两端等价。每个碰撞体至少明确中心坐标、尺寸、水平旋转角、是否阻挡玩家、是否阻挡子弹、是否阻挡视线及材质；统一使用米、`x/y/z`、弧度、中心坐标。窗户、护栏、可穿透木箱不能只用一个 `solid` 布尔值表达。视觉网格可比规则碰撞体复杂，但主要遮挡位置必须对齐。

地图加载顺序：读取规则数据 → 校验 ID/版本和数据边界 → 构造客户端碰撞世界与场景 → 根据 `nav` 建寻路网格 → 根据 `radar` 和碰撞体绘制雷达 → 玩家出生 → 开始同步。当前 `mapRuntime.dispose()` 可重复调用，释放地图场景根对象、几何体、材质、灯光及碰撞索引。返回主菜单时地图仍作为背景显示，所以不会卸载；未来真正切图时还需要先销毁角色、视角模型、环境和特效，再调用地图卸载并释放贴图。

目前 `shared/maps/validate.js` 是两端共用的规则入口：构建时、客户端创建地图运行时、服务端注册地图时会检查地图 ID、正整数版本、非空名称、有序边界、两队出生点、寻路范围与雷达参数。服务端注册时还检查碰撞体尺寸与出生点投影是否与共享规则一致。它检查的是数据形状和范围；出生点是否被具体场景几何挡住仍需地图几何检查与人工功能测试。后续新增地图时，应先使其通过此入口和对应地图数据测试，再注册到两端。

## 5. 房间协议与服务端改造

1. `create` 请求增加 `mapId`。服务端只接受注册表中已启用且支持当前模式的地图，忽略客户端提交的出生点、碰撞体和版本。无 `mapId` 时默认 `transport-ship`，兼容旧客户端。
2. `roomBrief` 和房间列表继续返回 `map`，增加可选 `mapVersion`；等待页按 ID 显示名称和海报。等待中房主暂不切图，先保证地图在创建后不变，降低比赛中途加入的复杂度。
3. 普通开局和中途加入的 `start` 消息都携带 `map`、`mapVersion`。客户端在开始发送位置和出生请求前加载对应地图；若本地缺失或版本不匹配，显示错误并留在房间，不得在错误地图上开局。
4. `server/combat.js` 保留射线与人体命中等通用算法，改为 `combatFor(mapId)` 或显式传入 `mapRules`。`handleRespawn`、`st` 位置范围/穿墙检查、枪/刀/手雷遮挡均从 `room.map` 取同一套服务端碰撞体。缓存可按 `mapId + version` 建立，不能按全局当前地图切换。
5. bot 由房主在所选地图上运行，路线和守点从地图包读取；不支持 bot 的地图应在创建房间时禁止补 bot。房间人数、比赛时长和得分仍由模式规则管理，不放进几何地图数据。
6. 服务端静态资源允许列表随构建产物和地图资源更新，显式校验路径、MIME 和缺失文件；不把任意客户端路径直接映射到文件系统。

## 6. 分阶段实施与中途测试

每个阶段都应停在**可启动、可回退**的状态；不能把“提取源码”和“接入新地图”合成一个无法中途运行的大改动。阶段验收失败时先修复该阶段，再继续。阶段 0–3 的拆分已实现；本轮接入阶段 4 的选图入口与协议，第二张地图和跨地图加载仍暂缓。

| 阶段 | 改动 | 本阶段即可运行的检查 | 完成标志 |
| --- | --- | --- | --- |
| 0. 基线 | 记录现有页面、服务端和运输船关键行为，不改产品逻辑 | 启动服务，打开原游戏页及测试台；记录出生、遮挡、bot、雷达和现有房间流程 | 后续改动有可对照的行为基线 |
| 1. 提取源码 | 从 HTML 提取样式、游戏脚本，第三方 Three.js 与业务代码分开；引入确定版本的构建脚本，保留原页面 URL | 脚本语法检查、资源路径检查、单机开局与现有联机入口冒烟 | 运输船仍可玩，源码可独立阅读和调试 |
| 2. 功能拆分 | 抽出游戏生命周期、渲染、移动碰撞、角色、武器、HUD、联机适配；保持相同调用顺序和数值 | 对照阶段 0 检查移动、开枪、死亡复活、HUD、退出再进入；现有房间流程仍可用 | 共享功能不再依赖运输船代码内部变量 |
| 3. 地图模块 | 将运输船视觉、出生、碰撞、导航和雷达配置收进独立地图包；客户端通过地图加载接口使用它；服务端仍只注册运输船 | 单机和现有联机分别检查出生点、遮挡、窗户、跳跃、bot 寻路、雷达；多次进出检查状态不重复 | 运输船通过地图接口加载，当前唯一地图行为不变 |
| 4. 房间选图（仅运输船） | 更新 `create`、`start`、中途加入协议及 UI；提供可用地图列表 | 无效地图拒绝、版本不匹配、旧客户端默认运输船、现有房间流程回归 | 可以为房间选择已注册地图 |
| 5. 第二张地图（暂缓） | 先增加一张简易白模团队竞技地图，再补视觉资源 | 两个房间同时运行不同地图，分别验证出生、移动、射击和中途加入 | 两张地图互不串数据 |

每个阶段独立验收后再进入下一阶段。选图协议已支持从服务端目录选择 `mapId`，旧客户端省略该字段时默认运输船；目前目录只有运输船。若当前不创建任何测试房间，可先用现有页面和模拟协议做中途测试，但“真人双人对局无回归”必须记录为待验收，不能据此宣称联机改造完全通过。

### 当前实现与分工

- `src/vendor/` 保存第三方后处理代码；`src/client/core/` 保存渲染器、碰撞与寻路和游戏主循环；角色、武器、音频、特效、HUD、雷达、触控各在对应目录。`web/game.js` 是生成产物，修改源码后运行 `cd server && npm run build:game`。
- `src/client/maps/transport-ship/` 包含贴图、场景、环境及地图包入口。主循环通过地图包创建贴图与环境、设置灯光和菜单镜头；地图注册表创建地图运行时并管理场景资源。HUD 的地图名称取 `rules.displayName`。
- `shared/maps/transport-ship.json` 提供两端一致的地图 ID、版本、边界、20 个出生点、寻路范围、雷达和 bot 路线。`shared/maps/validate.js` 在构建、客户端加载与服务端注册时校验数据。
- `server/maps/transport-ship.js` 保留服务端 145 个简化射线碰撞体，`server/combat.js` 是通用命中算法。客户端使用场景内更细的移动和射线碰撞体；两者的语义边界见[地图碰撞数据契约](地图碰撞数据契约.md)。当前尚未把所有碰撞体统一成一份 JSON。
- `src/client/multiplayer/hooks.part.js` 定义联机可扩展钩子；`web/mp.js` 从钩子注册、读取原方法，联机开局会检查房间地图 ID 与本地版本。建房页从服务端地图目录显示可选项，房间列表与等待页展示地图，正常开局和中途加入均传送 `map`、`mapVersion`。新增地图时仍需将 `getRegisteredMap("transport-ship")` 改为从房间协议读取的地图 ID，并实现完整切图加载。
- 开发侧负责构建一致性、语法、规则、碰撞指纹、射线、雷达、bot 和联机钩子的白盒检查。使用者按[黑盒测试清单](架构拆分黑盒测试清单.md)验证实际画面、操作与现有房间联机流程。

## 7. 新地图与实际切换的后续验收重点

- **规则数据**：地图 ID 唯一、版本有效；出生点位于地图边界内、无阻挡且 BL/GR 不重叠；碰撞体尺寸和角度有效；客户端和服务端从同一份规则数据构建。
- **运输船不退化**：原有两队出生、集装箱通道、窗户射线、跳上高处、雷达位置和 bot 寻路与改造前一致；枪、刀、手雷的遮挡判断正确。
- **联机流程**：创建、列表、选队、开局、复活、中途加入、离开、再来一局均使用房间地图；同时运行两种地图时，位置边界、遮挡与出生点各自独立。
- **异常处理**：无效 `mapId`、地图文件缺失或版本不匹配时明确报错；客户端不能通过上报另一地图的坐标绕过当前房间校验。
- **运行与发布**：构建脚本能在干净环境产出页面所需资源；`/transport-ship-mp.html` 和 `/web/testbed.html` 仍可访问；地图资源路径能通过服务器正常返回。

## 8. 主要风险与取舍

现有大 HTML 中混有压缩后的 Three.js 和游戏代码，直接按文本切割函数容易破坏闭包依赖。先恢复可读源码和稳定构建，再抽模块。客户端与服务端碰撞体仍非完全相同：客户端还包含只影响移动或视线的物体，服务端有简化体；新增地图时需要按“阻挡玩家/子弹/视线”的语义逐项对照，不能机械复制某一侧。地图版本应在房间创建时锁定；部署新版地图时已有对局需继续使用旧版本规则，或按现有单进程重启策略结束旧局，不能让进行中的对局悄悄换碰撞数据。
