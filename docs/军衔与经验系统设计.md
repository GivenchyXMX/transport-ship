# 军衔与经验系统设计（v1 已接入，发放默认开启）

## 1. 目标与当前边界

- 每个已注册账号有永久累计经验（XP）和军衔；军衔只升不降。每局由服务器在比赛结束时结算一次，客户端只显示结果。
- 支持开局玩家和中途加入玩家；离线时已完成的结算仍可在下次登录后查看。
- 不提供客户端提交经验、击杀数、比赛结果或“请求结算”的接口。刷新页面、重放 WebSocket 报文、重复领取结算都不能增加 XP。
- **当前已完成真人命中判定的第一版改造**：客户端发送开枪方向，服务端按武器、弹药、射速、地图简化碰撞体和位置历史计算命中与伤害；旧 `hit{v,d,p,w}` 只对 bot 生效，不能改变真人血量和历史战绩。玩家的位置、视角仍由客户端输入，bot 仍由房主模拟；需通过双人实战持续核对地图碰撞和刷分限制。

`server/server.js` 管理房间、比赛结束和血量裁决；`server/leaderboard.js` 将真人击杀写入带 `match_id` 的 SQLite `combat_events`；`server/rank.js` 记录比赛、参与者和军衔流水。旧击杀事件没有比赛 ID，不追溯经验。默认 `RANK_XP_ENABLED=1`，可设为 `0` 暂停新比赛发放。

## 2. 军衔与升级曲线

初始为 1 级“列兵”，累计 XP 达到门槛立即升级。第 `L` 级升下一级所需经验为：

```text
need(L) = 100 + 40 × (L - 1) + 10 × (L - 1)²，1 ≤ L < 18
threshold(1) = 0
threshold(L + 1) = threshold(L) + need(L)
```

| 等级 | 军衔 | 达到本级的累计 XP | 升下一级所需 XP |
|---:|---|---:|---:|
| 1 | 列兵 | 0 | 100 |
| 2 | 二等兵 | 100 | 150 |
| 3 | 一等兵 | 250 | 220 |
| 4 | 上等兵 | 470 | 310 |
| 5 | 下士 | 780 | 420 |
| 6 | 中士 | 1,200 | 550 |
| 7 | 上士 | 1,750 | 700 |
| 8 | 少尉 | 2,450 | 870 |
| 9 | 中尉 | 3,320 | 1,060 |
| 10 | 上尉 | 4,380 | 1,270 |
| 11 | 少校 | 5,650 | 1,500 |
| 12 | 中校 | 7,150 | 1,750 |
| 13 | 上校 | 8,900 | 2,020 |
| 14 | 大校 | 10,920 | 2,310 |
| 15 | 少将 | 13,230 | 2,620 |
| 16 | 中将 | 15,850 | 2,950 |
| 17 | 上将 | 18,800 | 3,300 |
| 18 | 元帅 | 22,100 | 已满级 |

表格与公式都由服务端同一份版本化配置生成，前端只读取等级、门槛和进度。到达 18 级后仍记录累计 XP，但军衔保持“元帅”。例如，一局获得 138 XP 时，5 级升 6 级约需 4 局，17 级升 18 级约需 24 局；这只是平衡示例，正式数值应根据真实对局数据调整。

## 3. 单局经验规则

### 3.1 可结算条件

1. 比赛由服务器以 `goal`（达到目标分）或 `time`（到时）正常结束；`host-left`、管理中止等不发 XP，并显示原因。服务重启前未结束的比赛标记中断，不生成结算流水。
2. 房间没有 bot，开局时两边各有至少一名真实玩家。bot 击杀、bot 死亡不计军衔 XP；v1 中含 bot 的整局不计 XP，防止刷机器人。
3. 玩家已收到服务器 `start`，完成首次 `respawned`，且本局在战斗中的有效在线时长至少 60 秒。只进入房间选阵营、尚未点“加入战斗”的玩家获得 0 XP。中途加入且不足 60 秒的玩家获得 0 XP，并在房间页提示。
4. 同一账号在同一比赛中只结算一次；断线后再次加入同一局，战斗时长和战绩按账号合并，重叠时间不重复计算。

有效在线时长由服务端时钟从首次出生起累计，玩家离开或连接断开时停止；客户端上报的时长不参与结算。**当前尚未实现挂机行为识别**，玩家出生后挂机仍可能累计时长。后续需增加服务端行为信号与人工审核，避免误伤固定位置防守玩家。

### 3.2 经验公式

仅对满足上述条件的玩家计算：

```text
基础参与：30 XP
有效时长：2 × min(⌊有效在线秒数 / 60⌋, 10) XP
比赛结果：胜利 20 XP；平局 10 XP；失败 0 XP
真人有效击杀：8 × min(可计经验击杀数, 15) XP
致命爆头：2 × min(可计经验的致命爆头数, 10) XP
本局上限：210 XP
```

“有效击杀”必须来自服务端最终确认的死亡事件。同一击杀者对同一受害者每局最多有 **3 次**击杀贡献 XP；超出的击杀仍可计入本局比分与现有战绩榜，但不增加该局的击杀、爆头 XP。死亡不扣经验，也没有仅凭客户端上报的“伤害量”奖励。示例：打满 10 分钟、获胜、8 次可计经验击杀、其中 2 次致命爆头，获得 `30 + 20 + 20 + 64 + 4 = 138 XP`。

防止固定两人反复开 1v1 房间：同一对账号在滚动 24 小时内最多 **3 局** 1v1 比赛可获得军衔 XP；超过后该局两人均为 0 XP，结算页明确说明。该规则是降低刷分收益，不能消除使用多个小号的串通行为。

## 4. 服务端结算流程与存储

### 4.1 生命周期

```text
服务器创建 match_id → 记录参赛账号、阵营和首次出生时间
→ 记录服务器认可的战斗事件、离开/重连片段
→ goal/time 结束 → 用服务器数据计算每人 XP
→ 持久化比赛结果与最终参赛数据
→ 在一笔 SQLite 事务中写入结算流水和账号总 XP
→ 广播结算结果；离线玩家下次登录查询
```

`match_id` 必须由服务器生成（UUID），与可重复使用的房间 ID 分开。客户端发送的 `end`、`xp`、`kills`、`level` 等字段一律不能触发或改变结算。服务器先持久化正常结束的比赛结果及最终参赛数据，再在一笔独立的 SQLite 事务中写入每人的结算流水并更新总 XP。服务器可重复执行结算函数；数据库唯一约束保证每个 `(match_id, account_id)` 最多记账一次。结算事务失败时全部回滚，不广播成功结果；重启后重试已持久化完成但尚未结算的比赛。进程崩溃前未正常结束的比赛标记为中断，不补发 XP。

### 4.2 建议的数据表

| 表 | 关键字段与约束 | 用途 |
|---|---|---|
| `rank_profiles` | `account_id PRIMARY KEY`、`xp_total INTEGER NOT NULL CHECK(xp_total>=0)`、`updated_at` | 当前累计 XP；等级由版本化门槛计算 |
| `matches` | `match_id PRIMARY KEY`、`room_id`、`started_at`、`ended_at`、`reason`、`winner`、`rules_version`、`status` | 比赛身份与最终状态 |
| `match_participants` | `PRIMARY KEY(match_id, account_id)`、`team`、`first_spawn_at`、`active_seconds`、`kills`、`headshots`、`deaths` | 聚合同一账号在本局的参赛数据；断线重入不建第二条结算主体 |
| `combat_events` | 增加 `match_id`、服务器生成的事件 ID、击杀/受害账号、时间、致命爆头标记 | 将服务端认可的击杀归属到比赛；旧事件不追溯 XP |
| `rank_settlements` | `PRIMARY KEY(match_id, account_id)`、`xp_awarded`、`breakdown_json`、`xp_before`、`xp_after`、`rules_version`、`settled_at` | 幂等结算与审计流水 |

SQLite 写入使用 `BEGIN IMMEDIATE` 事务，在同一事务里插入结算流水并更新 `rank_profiles.xp_total`。`rank_settlements` 是可审计的经验来源；不得只改总 XP 而没有流水。规则调整只影响新比赛，已结算流水保留当时的 `rules_version`。当前账号、排行榜和军衔模块各持有 SQLite 连接，按进程内同步调用顺序写入同一个 WAL 数据库；击杀事件写入失败时会记录错误，该事件不会产生 XP。后续可将事件和军衔写入统一数据访问层，降低跨连接维护成本。

## 5. 抓包篡改与刷经验防护

| 风险 | 必要处理 |
|---|---|
| 重发“结算/领奖”请求 | 不提供此类写接口；结算仅由 `endMatch` 驱动，数据库用 `(match_id, account_id)` 唯一键幂等记账 |
| 改客户端的击杀数、经验值、军衔 | 这些字段不参与服务端计算；HTTP 只提供本人数据的只读接口 |
| 伪造 `hit`、爆头、武器伤害 | 真人 `hit` 已禁用；服务端按武器配置和地图简化碰撞体计算。上线 XP 前需实战核对地图遮挡、刀和手雷结果，并记录异常射击证据 |
| 伪造位置、穿墙或高速移动 | 当前先检查出生点、速度和移动路径；位置与视角仍由客户端上报。若要求更强的竞技防作弊，需要把移动模拟也迁到服务端，并持续完善碰撞与历史状态校验 |
| 与朋友反复互杀、短局刷分 | 60 秒最低参赛时间、每局奖励上限、同一受害者击杀 XP 上限、1v1 同对手次数上限；异常高频账号进入人工审核或暂缓发放 |
| 直接改服务器 SQLite 文件 | 限制服务器文件权限、隔离进程账号、定期备份和保留结算流水；拿到服务器写权限的人无法仅靠网页协议防住 |

HTTPS/WSS 保护传输链路，但玩家自己控制的浏览器可以构造任意 WebSocket 报文；不能把“有 Cookie”“请求来自游戏页面”当作战斗数据可信的依据。第一版服务端真人命中判定能挡住直接改目标、伤害和爆头报文，不能防住自动瞄准、串通刷分或拥有服务器写权限的人。军衔结算已接入，真实 XP 写入默认开启；实战验证及挂机识别仍需继续完善。

## 6. 接口与页面

- `GET /api/rank/me`：沿用当前标签页的 `X-Ship-Tab` 与 HttpOnly Cookie，返回本人的昵称、邮箱、累计 XP、等级、军衔名、升级进度、真人击杀与死亡、KDA 和已结束比赛的累计参赛秒数；不接受 `accountId` 指定他人。当前无助攻记录，KDA 按击杀数除以 `max(死亡数, 1)` 计算。
- `GET /api/rank/settlements?limit=20`：读取本人最近结算，含比赛时间、结果、各项 XP、未计经验原因。
- 比赛结束的 WebSocket `end` 消息增加服务端结算摘要；客户端断线时不影响记账，重新登录后从只读接口补看。
- 联机大厅顶部和房间名单显示军衔；右上角“个人信息”页展示邮箱、昵称、战绩、累计对局时长、军衔进度与最近结算；赛后显示“本局 +XP、累计 XP、升级前后军衔、距离下一级还差多少”。未达资格显示具体原因，不显示可领取按钮。主菜单在线名单按既有要求只显示状态，Tab 排行军衔展示尚未接入。

## 7. 实施顺序与验收

1. 固定并版本化等级表、XP 参数和结算资格；新增数据库表及迁移。旧账号从列兵 0 XP 开始，不从现有 `combat_events` 回填。
2. 给比赛、参赛者和服务端认可的击杀事件增加持久化 ID；记录中途加入、离开、断线和比赛结束原因。
3. 实现事务结算与唯一键去重；确认重放消息、重复调用结算、进程重启都不会重复加 XP。
4. 改造命中与移动验证，限制伪造击杀；在此之前保持真实 XP 写入开关关闭。
5. 已接入只读接口、军衔展示和结算 UI，默认发放 XP；还需用实际对局数据检查升级速度、1v1 限制和误判。Tab 排行内的军衔展示仍待补充。

验收重点：客户端发送任意 `xp/level/end/kills` 消息不会改 XP；同一局同一账号最多一条结算；未参战、低于 60 秒、含 bot、中断和超出 1v1 次数的比赛均给出 0 XP 与原因；中途加入按实际参赛时长结算；正常比赛的 XP 明细与服务器事件一致。
